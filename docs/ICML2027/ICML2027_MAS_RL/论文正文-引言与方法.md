# Epistemic Planning: Training the Planner as a World Model of the Multi-Agent System

**认知规划：把 Planner 训练成多智能体系统的世界模型**

> 正文草稿（Introduction + Method）。压缩自 `MAS_RL_思考-润色版.md`，不替代该思考稿。不含实验实现。

## 1 Introduction

工具型多智能体正在成为 Agentic RL 的默认形态。一个 Planner 读取任务，选出子目标和工具；一个 Executor 把这个选择变成真实调用；结局对错再广播回 Planner。AgentFlow 用 Flow-GRPO 把轨迹级成败写进每一步规划，Search-R1 用多轮搜索的最终答案训练检索策略，EPC-AW 在同一条工具链上用跨 agent 一致性挑选计划。这些工作的算法不同，共享同一个未被写出的假设：任务成功，Planner 就会变好。

这个假设把两种成功混在了一起。一种是 Planner 理解了 Executor 能做什么、工具会返回什么，所以计划成立。另一种是同一条计划被反复重试，直到某一次调用碰巧命中。奖励只看见结局，看不见区别。于是策略学到的是执行层的捷径：Retry，直到答案碰上。社区的回应是把奖励写得更密——过程奖励、验证器、重试次数上限。监督对象没有变。只要优化目标仍是外部回报，下一步捷径就仍有梯度。

缺的不是另一项奖励，而是 Planner 从未承诺过的那一层预测。以 HIVE 的 `NextStep` 为例，Planner 只输出理由、上下文、子目标和工具名。Executor 在这一步之后才生成 query、代码或 URL。工具返回什么、会不会超时、证据是否对得上子目标，都不在 Planner 的输出里。一次超时、一次搜到了但证据不对、一次计划本身就错，回到学习信号里是同一个成败比特。失败无法指出该改参数、该换工具，还是该改对环境的判断，下一步计划也就无从被改写。

本文把 Planner 定义为多智能体系统本身的世界模型，而不是任务策略。它在同一步写出两样东西：一份计划，以及这条计划若被执行将会发生的过程——Executor 如何绑定参数，工具如何返回证据，失败会落在哪一个位点。候选只在想象中打分。得分最高的一条才进入真实执行。学习信号取自想象轨迹与真实轨迹的三层残差，而且只取其中改写了下一步计划的那一部分。成功是确认性证据，失败是修正性证据。一次没有带来新计划的重试，信息增益趋近于零，不必再靠手工上限把它裁掉。

本文的贡献有三点。

- 把 Agentic RL 的优化对象从任务策略改为 Planner 对 Executor、Tool 与 Environment 的内部模型。任务成败保留为效用项，不再单独充当认知是否进步的证据。
- 给出一套可计算的机制：双输出 Planner、想象门控、三层残差，以及「残差只有改变了后续 plan 才计入信息」的定义。
- 给出可执行实例。Executor 与 Diagnoser 冻结，只更新 Planner。主环使用可复现的本地工具。StructAgent 的类型化动作只作为信念迁移的第二环境，不进入训练环。

与邻近工作的界限可以先说清，展开留待 Related Work。AgentFlow 优化的是哪一个工具能让最终答案正确。EPC-AW 用跨 agent 一致性校准可行性判断，被选中的计划仍然发起真实搜索。HIVE 的 sibling 对照发生在真实执行之后，记录的是换工具或换参数的事后差异。WebDreamer 在行动前想象网页状态，用来挑选更可能完成任务的动作。上述工作都没有把「对 Executor–Tool 执行过程的预判误差，以及该误差是否改写了下一步计划」当作 Planner 的学习对象。

## 2 Method

### 2.1 问题设定

一个任务实例是查询 $q$。系统在每一步 $t$ 维护信念

$$
M_t = (\mathrm{Cap},\ \mathrm{ToolRel},\ \mathrm{Env},\ \mathrm{Rec}).
$$

$\mathrm{Cap}$ 记录工具对所需能力的覆盖，$\mathrm{ToolRel}$ 记录工具可靠性，$\mathrm{Env}$ 记录环境约束（索引覆盖、超时、权限），$\mathrm{Rec}$ 记录哪一类失败可以用哪一种修复接住。$M_0$ 用 HIVE `capability.py` 的四能力表初始化：retrieve、compute、perceive、synthesize。这张表只作为先验。此后对 $M_t$ 的写入只来自第 2.4 节的残差规则。

角色沿用 HIVE 的三角色，但职责改写如下。Planner $\pi_\theta$ 是唯一可训练模块，也是世界模型：给定 $(q, M_t)$，它产出计划与想象执行。Executor 与 Diagnoser 冻结。Executor 把被选中的计划落实为 `ToolCommand` 并调用工具。Diagnoser 读取工具原文，给出 `SUBGOAL_COMPLETE` 或 `SUBGOAL_INCOMPLETE`，以及已有的 `failure_type`。冻结这两角色，是为了让残差所对照的真实量不随 $\theta$ 一起移动。

主循环的工具集是

$$
K_{\mathrm{main}} = \{\texttt{Python\_Coder\_Tool},\ \texttt{LocalBM25}\}.
$$

`LocalBM25` 索引 HotpotQA / 2Wiki 的本地语料，或一份 Wikipedia dump。返回原文片段，不经过第二遍语言模型摘要。`Base_Generator_Tool` 只在回合结束时把已核实证据写成最终答案，不进入候选竞争。在线 Google Search、Wikipedia Search、Web Search 不在每步循环中调用。它们只保留为少量分布外探针，用来测量已经写下的 $\mathrm{ToolRel}$，不参与训练梯度。

### 2.2 结构设计

每一步，Planner 采样 $K=4$ 个候选。一个候选是一对

$$
c = (\pi,\ \hat{e}).
$$

计划头

$$
\pi = (\mathrm{subgoal},\ \mathrm{tool},\ H)
$$

给出子目标、所选工具，以及这一步要检验的假设 $H$（例如「LocalBM25 覆盖该实体」或「Python 标准库足够完成该计算」）。想象执行头

$$
\hat{e} = (\texttt{executor\_args},\ \texttt{tool\_dynamics},\ \texttt{predicted\_obs},\ \texttt{failure\_locus})
$$

给出四件事：Executor 将发出的参数，工具返回的形态（空结果、报错类型、证据种类），预期观测是否满足子目标，以及若失败，失败落在参数、工具还是结局。

候选的比较发生在任何外部调用之前。记想象得分为

$$
S(c) = U(\hat{e}) + \lambda\,\mathrm{IG}(H,\ \texttt{failure\_locus}) - \beta\,\widehat{\mathrm{Cost}}(c).
$$

$U(\hat{e})\in\{0,1\}$ 表示想象观测是否满足子目标。$\mathrm{IG}$ 度量该失败位点对当前假设集的划分：若 $M_t$ 中有一组互斥假设，而 $\texttt{failure\_locus}$ 使其中一部分被排除、另一部分被保留，则 $\mathrm{IG}$ 取被排除假设的先验质量；若失败位点与所有假设相容，则 $\mathrm{IG}=0$。这是诊断性试探的分数，不是动作熵。$\widehat{\mathrm{Cost}}$ 使用工具类别的已知代价，不依赖真实耗时：本地检索为 $1$，代码执行为 $2$，在线搜索为 $8$。在线搜索因此几乎不会在想象中胜出，与它被移出主循环一致。

只执行

$$
c^\star = \arg\max_c S(c).
$$

其余候选不产生 `ToolCommand`，也不写入工具日志。被选中的计划交给冻结的 `execute_tool_command`。

```text
M_t
  → Planner 采样 K 个 (plan, imagined execution)
  → 在想象中计算 S(c)
  → 仅 c* 进入 Executor
  → Diagnoser 读取工具原文
  → 三层残差更新 M_{t+1}
  → 在 M_{t+1} 下产生下一步计划
```

### 2.3 算法 1：想象门控

**输入** 查询 $q$，信念 $M_t$，候选数 $K$，冻结的 Executor。  
**输出** 被执行的候选 $c^\star$，真实轨迹 $e$。

1. 从 $\pi_\theta(\cdot\mid q, M_t)$ 采样 $c_1,\ldots,c_K$。每个 $c_i$ 同时包含 $\pi_i$ 与 $\hat{e}_i$。采样时不调用 $K_{\mathrm{main}}$。
2. 对每个 $c_i$ 用第 2.2 节的公式计算 $S(c_i)$。$U$、$\mathrm{IG}$、$\widehat{\mathrm{Cost}}$ 都只读 $\hat{e}_i$ 与 $M_t$。
3. $c^\star \leftarrow \arg\max_i S(c_i)$。并列时取 $\widehat{\mathrm{Cost}}$ 更小者。
4. 若 $c^\star.\pi.\mathrm{tool}\notin K_{\mathrm{main}}$，丢弃该候选并在剩余候选中重选。若全部被丢弃，本步不调用工具，记 $C_t=0$，信念不更新。
5. 调用冻结 Executor，得到 `ToolCommand` 与工具原文。Diagnoser 给出 `subgoal_conclusion` 与 `failure_type`。三者组成真实轨迹 $e$。
6. 返回 $(c^\star, e)$。

想象门控把「生成多个计划」和「发起多次搜索」拆开。候选数 $K$ 增加的是 Planner 的前向计算，不是工具延迟。

### 2.4 算法 2：三层残差与信念更新

真实轨迹取三处已经存在的字段，不另请语言模型概括工具输出。

| 层 | 预判 | 真实量 | 不一致时写入 |
|---|---|---|---|
| 参数 | $\hat{e}.\texttt{executor\_args}$ | `ToolCommand` 的参数 | Executor 落地方式 |
| 工具 | $\hat{e}.\texttt{tool\_dynamics}$ | 工具原文中的报错类型、是否为空、证据形态 | $\mathrm{ToolRel}$ 或 $\mathrm{Env}$ |
| 结局 | $\hat{e}.\texttt{predicted\_obs}$ 是否满足子目标 | `SUBGOAL_COMPLETE` / `SUBGOAL_INCOMPLETE` 与 `failure_type` | $\mathrm{Cap}$ 或 $\mathrm{Rec}$ |

参数层的不一致用参数字段的精确匹配：query 字符串、代码入口、检索词。不比较自由文本解释。工具层只读结构化标记：异常类型、空返回、命中条数是否为零。结局层是二值，并带上 Diagnoser 已有的 `failure_type`。

信念更新是确定性规则，分组沿用 Diagnoser 的 `REASON_INSTRUCTION`，不新训练诊断器。

- 参数类，`entity_missing` 与 `schema_mismatch`：不降低该工具的 $\mathrm{ToolRel}$。把「此类子目标下 Executor 应使用的参数模式」写入 $\mathrm{Rec}$。
- `capability_mismatch`：将 $\mathrm{Cap}(\mathrm{tool},\mathrm{required})$ 置为假。下一步不得再把该工具选入需要该能力的假设。
- `backend_timeout`、空结果、`paywalled`：按固定步长下调 $\mathrm{ToolRel}(\mathrm{tool})$。空结果同时在 $\mathrm{Env}$ 中记下该查询未被索引覆盖。
- `belief_conflict`：用工具原文替换 $M_t$ 中与之冲突的 $\mathrm{Env}$ 条目。

信息是否计入，不由残差的幅度决定，而由下一步计划是否因此改变。记 $M_{t+1}$ 为上述规则作用后的信念，$M_t$ 为不更新的对照。分别在两个信念下各采样一条下一步计划 $\pi^{+}$ 与 $\pi^{0}$（温度与算法 1 相同，各一条，不执行）。定义

$$
I(\hat{e}, e) =
\begin{cases}
1 & \pi^{+} \text{ 与 } \pi^{0} \text{ 在 tool、subgoal 或 } H \text{ 上有任一字段不同},\\
0 & \text{否则}.
\end{cases}
$$

若本步真实调用与上一步的工具和参数相同，且 $I=0$，记为无信息 Retry。该事件的任务效用可以仍为成功，它的认知项为零。

**输入** $(c^\star, e, M_t)$。  
**输出** $M_{t+1}$，$I(\hat{e}, e)$。

1. 按上表计算三层是否不一致。
2. 用 `failure_type` 选择上面四条规则之一，写入 $M_{t+1}$。无 `failure_type` 且结局层一致时，只把该工具–能力对记为一次确认，不提高任务回报之外的权重。
3. 采样 $\pi^{+}\sim\pi_\theta(\cdot\mid q, M_{t+1})$ 与 $\pi^{0}\sim\pi_\theta(\cdot\mid q, M_t)$，只取计划头。
4. 按字段比较得到 $I$。返回 $M_{t+1}$ 与 $I$。

### 2.5 算法 3：只训练 Planner

Executor 与 Diagnoser 在两个阶段都冻结。梯度只进入 Planner 两个头的 token。

**阶段 A：监督校准。** 数据来自 HIVE 已有的 `inference_log` 轨迹。一条监督样本是 $(q, M, \pi, e)$，其中 $e$ 含真实 `ToolCommand` 与 diagnoser 标签。训练目标是让想象头重建已经发生的参数、工具标记和结局，计划头重建当时选出的工具与子目标。这一阶段的损失是两个头的token 负对数似然，没有 $I$，也没有真实意义上的「想象」。它的作用是让 $\hat{e}$ 在进入阶段 B 之前具备可比较的格式。阶段 A 结束时，$M$ 仍停在 `capability.py` 的先验，不把日志里的成败写进 $\mathrm{ToolRel}$。

**阶段 B：on-policy。** 对每个查询重复算法 1 与算法 2，直到子目标完成或达到步数上限。被执行候选的回报是

$$
R = U_{\mathrm{task}} + \lambda\, I(\hat{e}, e) - \beta\, C,
$$

其中 $U_{\mathrm{task}}\in\{0,1\}$ 是 Diagnoser 的结局层结论，$C\in\{0,1\}$ 是本步是否发生了真实工具调用。$I$ 依赖下一步计划，因此该回报在 $\pi^{+}$ 与 $\pi^{0}$ 采样完成之后才赋值，信用只记在 $c^\star$ 上，不记在未被执行的候选上。同一查询的 $K$ 个候选组成一组，用组内标准化优势更新 $\pi_\theta$：

$$
A(c_i) = \frac{R_i - \mathrm{mean}(R)}{\mathrm{std}(R)+\epsilon},
$$

未被执行的候选 $R_i = -\beta\cdot 0 = 0$，它们只作为组内基线出现，不接收「假执行」的任务效用。标准化之后，对 $c^\star$ 两个头的对数概率做策略梯度。$\epsilon$ 取 $10^{-8}$。组内方差为零时跳过该组，避免把全相同的想象打成分母。

阶段 B 的一步可以写成：

1. 算法 1 采样并只执行 $c^\star$，得到 $e$ 与 $C$。
2. 算法 2 更新 $M_{t+1}$ 并计算 $I$。
3. 用上式得到 $R$，组内标准化，只对 $c^\star$ 反传。
4. 下一步的 Planner 条件改为 $M_{t+1}$。

$\lambda$ 与 $\beta$ 不在阶段 A 出现。阶段 B 中 $\lambda$ 固定为 $1$，$\beta$ 固定为 $0.1$，不按验证集搜索。这两个数的作用是把量纲对齐：$I$ 与 $U_{\mathrm{task}}$ 同为 0/1，$C$ 也是 0/1。它们不是第二套奖励工程。

### 2.6 迁移接口

StructAgent 不出现在算法 1–3 的训练环中。迁移时读取阶段 B 结束时的 $M$，作为 StructAgent planner 的额外条件，不改其 verifier。比较限于类型化动作：LibreOffice Calc 的 `calc_*`，以及只读探针 `file_grep` 与 `shell_command`。原有的 `<expected_post_state>` 扩展为同一 $\hat{e}$：除屏幕应呈现的结局外，写出将调用的动作名与参数、探针预期返回、失败位点。残差的真实量改为 verifier 探针的布尔结果与动作参数，不用截图像素，也不用 pyautogui 坐标。要报告的量是：在同一子目标下，带有 $M$ 与不带 $M$ 时，planner 的下一步工具或动作名是否不同。OSWorld 的任务成功率不作为本方法的优化目标。
