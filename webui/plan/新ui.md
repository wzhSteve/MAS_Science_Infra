## 一、产品的中心：不是编辑工作流，而是设计并执行训练实验

你的产品应该让用户完成这件事：

**定义一个 MAS 怎样完成任务，指定其中哪些部分被训练，再定义训练数据、奖励与训练策略，最后启动一次训练。**

这里有三个不同的对象：


| 对象 | 用户关心什么 | 界面职责 |
| --- | --- | --- |
| 实验方案 | 我要训练什么、怎样训练 | 可编辑的工作流与训练配置 |
| 训练运行 | 这次到底用了什么配置、执行得怎样 | 不可变快照、运行状态、日志、停止 |
| 单题调试 | 这个工作流能否按预期完成一道题 | 输入问题、查看回答和执行过程、定位节点 |


**单题调试是设计时的辅助工具，不是与训练并列的产品主流程；控制台是某次运行的输出窗口，不是上述对象的总导航。**


## 二、当前界面具体错在哪里


### 1. 最重要的训练配置，被降级成了画布旁边的“设置”


现在页面大部分面积始终留给画布，训练相关内容却挤在右侧抽屉里。


这会传递一个错误信号：


工作流是主体，模型、数据、训练策略只是它的附属设置。

但对于可编排 RL 平台，**工作流和训练定义共同构成实验**。配置训练时，训练配置理应占据主工作区，没有必要让一大片暂时无关的画布持续占位。


### 2. 当前分类是在整理参数，不是在组织用户决策


“模型绑定、数据与采样、训练方案、评估与诊断、执行环境”存在明显的层级混杂：



- “模型绑定”是技术操作，不是用户目标。

- 数据集与 Rollout 采样不是一回事，只因为都叫“采样”就放一起。

- “训练方案”听起来应该包含模型、数据、算法和资源，实际却主要是优化参数。

- Harness 诊断不等于奖励定义，也不应该成为开始训练前必经的一项。

- GPU 在顶栏编辑，资源参数在环境页编辑，训练配置缺少完整视图。



**平行分类本身并没有错；错的是这些分类并不处于同一层级，也没有表达它们如何共同形成一次训练。**


### 3. 缺少 RL 平台最关键的解释


现在容易找到学习率、模型路径，却不容易直观回答：



- 工作流里的谁会被训练？

- 哪些 Agent 只是参与执行？

- 更新的是哪份模型权重？

- 什么结果会获得奖励？

- 算法和分支采样怎样作用在这个工作流上？



这些不是高级细节，而是这个产品区别于普通工作流平台、普通模型训练表单的核心。


### 4. 控制台的管理界面比输出界面还突出


目前外层标题、左侧任务菜单、历史选择、刷新记录、配置下次训练、再次启动、内部状态栏逐层叠加。


用户看到的不是“程序正在输出”，而是“底部又嵌了一个小应用”。


**控制台的感觉来自输出优先、上下文稳定、控制克制，不是来自深色背景或终端图标。**


## 三、推荐的新结构：一个实验工作区，两个配置视图，一个纯输出控制台


不做强制逐步向导，也不另建一套训练应用。


实验工作区的主体只有两个视图：


**工作流｜训练配置**


它们是同一份实验方案的两个编辑视角，共享保存状态和唯一的“开始训练”入口。运行记录是已有执行的查询入口，不再混进设置。


### 工作流视图


Plain text






```
实验 / arpo_e2e        有未保存修改       [保存实验] [开始训练]

[工作流]  [训练配置]                           [训练记录]

┌─────────────────────────────────────────────────────────┐
│ [+ 添加节点] [单题调试]                                  │
│                                                         │
│               MAS 编排画布              选中对象的属性   │
│                                                         │
│        Agent / Router / 执行连接          Prompt、模型引用 │
│        可训练对象标识、分支位置标识         节点/边局部属性  │
│                                                         │
└─────────────────────────────────────────────────────────┘
控制台 · 无活动训练                                      [展开]

```





### 训练配置视图


Plain text






```
实验 / arpo_e2e        有未保存修改       [保存实验] [开始训练]

工作流  [训练配置]                            [训练记录]

┌──────────────┬──────────────────────────────────────────┐
│ 训练对象      │ 哪些 Agent 参与训练、使用哪份初始权重     │
│ 数据与奖励    │ 使用哪些题目、怎样判断结果好坏             │
│ 训练策略      │ 算法、候选生成、分支、优化参数             │
│ 执行资源      │ 当前执行端、GPU、并行与显存配置            │
│              │                                          │
│ 页内定位目录  │ 主区域是有顺序的配置正文，不是窄抽屉       │
└──────────────┴──────────────────────────────────────────┘
控制台 · 无活动训练                                      [展开]

```





这里左边是**同一份训练配置的页内目录**，不是四套互相独立的功能。正文按用户决策顺序组织，可以直接跳转，不要求从第一步填到最后一步。


对于已有实验，默认展示当前配置摘要；展开需要修改的部分。高级参数就近折叠，不再有一个装下所有字段的“高级设置”。


## 四、训练配置应该怎样组织


### 1. 训练对象：先回答“训练谁”


这里应该先展示：



- 参与训练的 Agent。

- 本次使用的初始模型权重。

- 其余 Agent 的执行模型来源。

- 当前训练后端实际支持的训练范围。



画布上的 Agent 应有明确的“参与训练”标识。训练对象区域展示汇总，并能定位到画布中的对应节点；**不能再维护另一份互不一致的 Agent 勾选状态。**


模型不再集中进一个笼统的“模型绑定”标签：
























| 模型用途 | 所属位置 |
| --- | --- |
| 被优化的初始权重 | 训练配置 → 训练对象 |
| 工作流默认推理连接、节点模型引用 | 工作流的全局属性/节点属性 |
| 模型资源登记、连接信息管理 | 全局模型资源库 |



资源库负责“有哪些资源”，实验负责“这次使用哪个”。不需要用户在多个地方重复登记、绑定和保存。


还有一个必须正视的实现边界：当前启动代码会从 `trainable_agents` 中取第一个传给 `--active-agent`。**因此不能仅凭画布多个勾选，就让界面承诺“多个 Agent 的独立模型同时训练”。** 新界面必须明确声明配置意图与本次实际训练对象之间的关系；不支持的组合应阻止启动，而不是隐藏差异。


### 2. 数据与奖励：回答“学什么、怎样算好”


这一部分包括训练集、验证集、任务字段，以及当前训练使用的奖励规则。


关键不是立刻增加一个复杂的奖励编辑器，而是：


**用户至少应该能知道当前 Reward 从哪里来、评估什么。**


对于底层已支持且可配置的规则，提供编辑；当前固定的实现，显示只读说明；尚未真正贯通的节点级 credit、实时 reward hacking 检查，不放一个看似可用的开关。


同时明确：



- 数据预览是看训练输入，不调用模型。

- 验证数据与评估频率属于训练配置。

- Harness 事后诊断不是训练 Reward。

- 不恢复独立采集或批量试跑。



### 3. 训练策略：把算法、Rollout 生成与优化放回同一个上下文


现在“算法在数据与采样，优化在训练方案”的分裂需要结束。


新的组织顺序是：


**训练方法 → 候选与分支生成 → 参数更新方式**

例如选择 ARPO 后，用户在同一区域理解每题候选数、初始 Rollout、分支位置和触发规则，再按需展开学习率、批次、KL 等优化参数。


底层仍可分别保存到 `workflow.sampling` 和 `rl.yaml`；**配置存在哪个文件，不应该决定用户在哪里编辑。**


分支位置有一个特殊点：它依赖工作流结构，不能只靠一串节点 ID 配置。因此建议：



- 训练策略中集中维护分支规则。

- 点“选择位置”进入画布定位已有节点或边。

- 画布上的分支标识能跳回同一个规则编辑器。

- 不复制第二套 Branch Site 表单。



选择不使用分支的策略时，隐藏不适用的编辑项，但不要静默删除原来的分支配置；明确其当前不生效即可。


### 4. 执行资源：回答“在哪里、用多少资源跑”


GPU 的编辑权收回这里，和并行 Runner、Tensor Parallel、显存比例、运行档位放在一起。


顶栏最多展示当前执行端或资源摘要，不再单独承担训练参数编辑。


还要区分：



- 浏览器所在机器。

- Control 实际连接的执行端。

- 该执行端能读取的模型和数据路径。



目前没有远程调度能力，就展示当前执行端，**不要先画一个实际上不能调度的服务器选择器**。


## 五、控制台重新定义：只负责观察和控制这次训练


**删除控制台左侧“训练日志 / 真实调试”菜单。**


训练开始后，底部自动展开并选中服务端返回的准确 run，默认给足日志高度，可以继续最大化。


Plain text






```
控制台   当前运行 ▾   ARPO · 运行中 · 00:12:36
                         [停止] [本次配置] [最大化] [收起]

[搜索日志]                        [跟随末尾] [复制] [下载]
────────────────────────────────────────────────────────
Loading model weights...
Initializing rollout workers...
...

```





这里只有三层：


**一行运行上下文、一行输出工具、日志正文。**


具体取舍如下：












































| 内容 | 去哪里 |
| --- | --- |
| 开始训练 | 实验工作区唯一主按钮 |
| 模型、算法、GPU 编辑 | 实验方案 |
| 停止当前运行 | 控制台运行标题栏 |
| 本次不可变配置 | “本次配置”只读详情 |
| 最近运行切换 | 标题栏紧凑选择器 |
| 历史列表、筛选、比较 | 训练记录 |
| Reward/Loss 曲线、Rollout Tree | 所属运行的分析详情，数据归属可靠后接入 |
| 单题问题输入、回答与轨迹 | 工作流调试工具 |



没有训练时，控制台默认收起，不占一个巨大空白区域，也不再摆第二个“检查并启动训练”。


查看历史时明确显示“历史运行”；运行结束不清空日志；收起不停止；暂停跟随不暂停训练。停止只针对当前查看且可控的运行。


### 单题调试从控制台拆出去


保留画布工具栏的“单题调试”，打开画布旁的调试面板：



- 上方输入问题并执行。

- 下方连续展示答案和执行过程。

- 点击过程定位画布。

- 当前模型以摘要展示，修改时跳到它的唯一配置位置。

- 调试历史放在这个面板内部，不再占用模糊的全局“运行记录”名称。



它可以扩大查看，但不与训练日志竞争同一个容器。Mock 放在开发入口，不占正常训练流程的位置。


## 六、“开始训练”必须成为真正的流程终点，而不是普通按钮


用户不应再记住“保存设计”“保存训练参数”“保存绑定”的顺序。


建议提供统一的 **保存实验**。内部仍可保存多个文件，但界面必须准确报告部分失败，不能假装存在跨文件事务。


点击“开始训练”后：



1. 有修改时明确提示保存本次实验修改；保存失败或期间又产生新编辑，则不能继续启动。

2. 对保存后的版本执行检查。

3. 展示一张精简确认单：训练对象、初始权重、数据与奖励、策略、执行资源。

4. 检查失败直接定位到对应字段；通过后确认启动。

5. 返回 run ID 后打开控制台，不再让用户自己寻找日志。



编辑时可以显示“尚缺训练数据”等局部提示，但不能把它标成“已可训练”；**实际可启动性以启动前检查为准。**


训练期间继续编辑，页面明确显示“修改用于下次运行”。当前运行的快照不变；如果当前后端不允许同实验并行训练，则不提供会覆盖它的启动操作。


## 七、这次重构的实施边界


建议按三个连续阶段推进，而不是再次整体堆功能：



| 阶段 | 关键交付 |
| --- | --- |
| 主结构调整 | 撤销总括式“实验设置”抽屉；建立工作流/训练配置双视图；拆出单题调试；控制台取消任务侧栏 |
| 配置与启动收口 | 按训练对象、数据奖励、策略、资源重新接线；唯一编辑来源；统一保存与启动检查 |
| 运行闭环 | 精简日志头部；训练记录与调试记录分开；具备可靠 run 归属后再接指标、树和产物 |



已有的增量日志、虚拟化、快照和安全停止逻辑应复用，不重写。React 层保持实验草稿在视图切换时不丢失，日志更新限制在输出组件内；隐藏日志停止订阅，不让画布跟着日志刷新。


这套方案的判断标准不是“菜单是不是更整齐”，而是：**用户能否在同一个实验中清楚地配置“训练谁、学什么、怎样训练、用什么资源”，然后点击开始训练，看到属于这次运行的真实输出。**

### 参数侧栏布局落地

- 唯一顶栏保留实验图标与名称、GPU、保存状态、保存实验和开始训练，不提供实验切换下拉框；模型与数据、更多功能位于顶栏右侧。
- 左侧约 324px，直接编辑训练对象、数据与奖励、训练策略、执行资源四组参数，不作为页面导航。常用字段直接显示，低频字段折叠；分支规则可扩大同一份表单编辑，画布暂时隐藏而不卸载。
- 实验内模型选择仅引用已有共享资源，不展示资源登记、搜索分页和单独绑定保存。初始权重与执行模型分开，默认推理资源位于训练对象的“执行模型”折叠项；旧模型路径保留折叠兼容入口。
- 数据路径集中在“模型与数据 → 数据”登记和编辑，持久化到 `resources/datasets.yaml`；侧栏只选择训练集和验证集，不编辑路径或奖励规则。实验保存选中的服务器路径，不随共享目录后续修改而自动改变。
- 保存实验复用已注册草稿，先保存工作流和训练参数，再保存模型绑定；失败明确报告已保存部分，保存期间的新编辑不会被当作已保存。调试临时输入和全局资源草稿不纳入实验保存。
- 画布仅保留添加节点和单题调试入口，不再另设“模型连接”。节点属性和调试共用右侧空间；Mock 保留在开发模式的执行模型折叠项内。
- 更多功能进入训练记录、诊断工具、实验监控和实验信息独立页面，不携带参数侧栏。控制台合并运行标题、最近运行选择与窗口控制，保留日志搜索、虚拟化、快照和安全停止逻辑。
- 画布、已访问的表单和调试会话保留挂载；日志更新限制在输出组件，控制台收起或实验隐藏时停止日志订阅。界面不展示布局或实现原理说明。
