# MAS 实验平台产品形态

## 产品定位

面向交叉领域研究人员的可视化 Agent 训练平台。用户无需先理解内部系统分层，即可搭建多 Agent 系统、调试任务、配置训练，并查看实验结果。

**以“实验”作为管理对象，以 MAS 画布作为编辑核心，以模型和数据作为资源，以训练作为主要执行目标，以调试作为局部辅助动作，以运行记录承载 Monitor、Rollout 和 Harness 结果。**

本文描述目标产品形态与页面关系，不是代码实施方案，也不表示其中的能力已经全部实现。

## 一、用户管理什么

产品围绕三类对象组织，不把内部技术模块直接变成同级导航。

| 对象 | 用户理解 | 包含内容 |
| --- | --- | --- |
| 实验 | 一个持续迭代的 MAS 研究方案 | Workflow、资源绑定、数据、训练方案、评估规则 |
| 资源 | 可以被不同实验复用的研究材料与能力 | 模型连接、数据集，以及后续扩展的工具等 |
| 运行记录 | 某个实验的一次实际执行 | 配置快照、执行状态、轨迹、指标、诊断与产物 |

第一版不增加复杂的“组织 → 项目 → 实验”层级。用户直接创建、打开和管理实验。

实验设计与实验执行必须分开：用户可以继续编辑草稿，同时上一版配置的训练仍在进行。运行中的任务不跟随草稿自动变化。

## 二、整体页面结构

- **实验首页**：浏览、创建、打开和复制实验；从模板开始。
- **资源管理**：管理模型连接和数据集，为实验提供可复用资源。
- **实验工作区**：以 MAS 画布为主体，结合节点属性、实验设置和局部调试。
- **实验运行记录**：查看该实验产生的训练、调试、采集和评估记录。
- **某次运行详情**：查看本次执行的进度、曲线、轨迹、诊断和产物。

页面路径：

**实验首页 → 打开实验 → MAS 工作区 → 开始训练 → 本次运行详情**

辅助路径：

**MAS 工作区 → 调试面板 → 查看结果 → 调整画布**

**MAS 工作区 → 实验设置 → 选择模型或数据资源 → 返回画布**

LLM、RL、Harness、Monitor 不再作为实验内六个平级页面中的独立入口。它们分别融入资源、设置和运行结果。

## 三、实验首页：像管理研究文件一样管理实验

### 首屏任务

回答三个问题：我有哪些实验、最近在做什么、从哪里开始新的研究。

首页的唯一主要操作是 **“新建实验”**。

实验以卡片或列表展示，包含：

- 名称与简短说明。
- MAS 结构缩略图或 Agent 数量。
- 最近修改时间。
- 最近一次训练或评估的状态。
- 打开、复制等低频操作。

实验名称和设计缩略图是视觉主体，参数摘要不是主体。没有历史运行的实验显示“尚未运行”，而不是空曲线或一排缺失指标。

### 创建与打开

新建时选择空白实验或 MAS 模板，填写名称后进入画布。模型、数据和训练参数可以之后补齐，不能要求先完成全部配置才能开始搭建。

点击实验进入工作区；点击卡片上明确的最近运行入口，进入对应运行详情。两种点击目标不能混淆。

复制实验创建一个独立设计，不复制“正在运行”状态，也不把原实验的执行记录算作新实验的历史。

### 状态表达

设计状态与运行状态分别显示，例如“最近修改于今天”与“上次训练已完成”。一个“运行中”徽标不能代替整个实验的状态。

## 四、实验工作区：画布是主场

### 工作区结构

| 区域 | 内容与职责 |
| --- | --- |
| 顶部工作栏 | 返回实验首页、实验名称、保存状态、调试、实验设置、开始训练 |
| 中央画布 | MAS 节点、工具、协作关系与直接编辑 |
| 左侧工具箱 | 添加 Agent、Tool、模板等，默认展开，只有用户点击叉号才关闭 |
| 右侧上下文面板 | 当前选中节点或连线的属性；也可承载实验设置入口 |
| 底部调试面板 | 输入任务、查看答案与执行过程，默认收起 |
| 运行记录入口 | 查看此实验已有的执行，不是另一个运行配置按钮 |

画布使用低对比度点阵背景，工作区充分利用可用空间。工具、属性和调试服务于画布，不把画布夹在多组大表单之间。

### 主要操作层级

| 操作 | 层级 | 行为 |
| --- | --- | --- |
| 开始训练 | 主操作 | 检查必要配置，确认本次方案后启动训练 |
| 调试 | 次操作 | 打开局部调试面板，不直接执行 |
| 实验设置 | 配置入口 | 管理模型绑定、数据、训练与评估方案 |
| 保存 | 编辑操作 | 保存设计，不启动执行 |
| 运行记录 | 查看入口 | 打开历史记录，不修改设计 |

可以有多种执行能力，但不能有多个同样突出的“运行”按钮。操作名称必须说明目的，不让用户猜测是在调试、采集还是训练。

### 编辑行为

- 点击节点或连线打开对应属性，未选中时不占用空属性栏。
- 节点属性围绕职责、Prompt、Skills、工具、模型绑定与训练参与设置。
- 连线属性只突出双方实体、关系方向与类型；连接点方位是画布外观操作。
- 打开设置、添加节点、调试或查看记录，不自动收起工具箱。
- 临时查看其他页面后返回，保留画布位置、未提交输入和草稿。
- 离开时若有未保存修改，应清楚提示保存或保留方式，不能静默丢失。

## 五、模型与数据：资源，而不是编排阶段

### 模型资源

模型连接在工作空间级管理，供多个实验引用。用户看到的是有意义的资源名称，例如“研究用 Qwen”“评估模型”“自部署推理服务”，而不是每个实验重复填写地址和密钥。

模型资源展示：

- 名称、来源和模型名称。
- 连接状态及必要能力说明。
- 凭据是否配置，不回显凭据。
- 可推理、是否具备训练接入条件等明确边界。

资源详情负责连接配置和维护，不要求用户在搭建画布时反复离开实验。

### 实验与节点如何使用模型

实验设置中选择一个默认推理模型，Agent 默认继承。

需要特殊模型时，在 Agent 属性中选择其他资源；明确显示“继承实验默认”或“已单独指定”，并提供恢复继承的操作。

多个 Agent 可以共享一个模型。Agent 是协作角色，模型是执行资源，不能暗示每增加一个 Agent 都要加载一份独立权重。

需要新增模型资源时，可以从选择器进入资源创建流程，完成后回到原实验和原选择位置。

### 推理与训练的区别

第三方 API 可以用于调试、参考 Agent 或评估，但不代表平台可以更新其权重。

训练方案必须明确哪些 Agent 参与更新、绑定哪一个可训练策略，以及是否共享策略。不能把“API 可访问”显示为“可以训练”。

实验可以使用一个模型进行前期调试，再配置另一项可训练资源；界面必须说明调试模型与训练策略的差别，不能暗中替换。

### 数据资源

数据集在资源管理中维护名称、来源、格式与任务规模等信息，实验通过选择资源使用数据。

训练数据和评估数据的用途分开标注。上传、导入和格式问题归入数据资源流程，不让 parquet 文件路径和读取依赖成为每次单题调试的常驻表单。

### 资源变更

共享资源被修改时，说明对引用实验后续执行的影响；已经开始的运行保留启动时信息，不被回写。

删除资源前提示使用中的实验。运行记录保留必要的脱敏快照，不因资源删除丢失结果归属。

## 六、实验设置：为这个 MAS 组织执行方案

实验设置是实验内部的上下文配置，不是一组脱离画布的平级应用。采用明确分组，简单配置先行，高级参数按需展开。

| 分组 | 用户需要决定的问题 |
| --- | --- |
| 模型绑定 | 默认推理模型是什么，哪些 Agent 有覆盖配置 |
| 数据与采样 | 使用哪些任务数据，如何采集，使用何种采样方案与预算 |
| 训练方案 | 训练哪些 Agent，如何绑定或共享策略，采用什么奖励与优化方案 |
| 评估与诊断 | 使用哪些评估数据和检查规则，在何时执行 |
| 执行环境 | 训练在哪个环境执行，模型与算力条件是否满足 |

默认提供可理解的预设，复杂参数不是用户第一次进入就必须填写的内容。已经完成的配置显示简短摘要，问题显示具体修复入口。

配置不完整不妨碍画布编辑。训练条件不满足也不妨碍使用已配置推理模型进行调试。

## 七、调试：局部辅助动作，实际产生 Rollout

### 调试面板的核心内容

- 任务输入。
- 当前实验及节点模型绑定的简短摘要。
- **“发送调试”**。
- 答案、实际工具调用、执行片段与错误详情。

顶部“调试”只负责展开面板，面板内“发送调试”才调用所选模型。两者是入口与执行的关系，不能都命名为“运行”。

### 默认行为

- 正式用户界面不提供 Mock / Live 选择，发送调试意味着使用所选模型实际执行。
- 条件不足则说明问题，不自动替换成模拟结果。
- Mock 留在内部开发能力中；如需演示，使用独立且清楚标记的演示入口。
- 不要求填写奖励、训练算法、训练 GPU 或批量采样参数。
- 单题调试不要求安装数据集读取能力。
- 真实调用的模型来源和可能的费用应清楚可见，但不需要每次阅读一大段技术免责声明。

### 调试结果

答案便于快速阅读，Rollout 保存完整过程。二者不是两套结果。

用户可以展开查看模型输入输出、工具调用和失败原因；有可靠归属时定位画布实体。定位是查看动作，不会修改 Workflow。

调试失败不意味着实验设计丢失。用户保留输入和草稿，修正后主动再次发送。

调试期间继续编辑时，结果仍绑定启动时的设计，明确提示后续修改尚未用于这次执行。

## 八、开始训练：唯一突出的执行主操作

点击“开始训练”后，呈现紧凑的执行摘要：

- 本次使用的 MAS 设计版本。
- 参与训练的 Agent 与策略资源。
- 数据和采样方案。
- 奖励、优化与评估方案摘要。
- 执行环境、资源占用和必要风险提示。

配置完整时确认启动；不完整时只列出真正阻断训练的问题，提供直达对应设置的入口，而不是再次展示整套表单。

启动后生成一条独立训练记录，并进入该次运行详情。返回画布后可继续编辑，但正在运行的训练不跟随草稿变化。

运行中再次点击主操作时，优先引导“查看当前训练”。只有产品确实支持并发且用户明确选择时，才提供另启一次训练；不能误触后重复占用资源。

远程 API 调试可用但没有训练算力时，仍允许完成设计与调试；“开始训练”解释缺少的条件，不制造已经具备训练能力的假象。

## 九、运行记录：所有结果都有明确归属

每次真实执行产生运行记录，类型清楚区分为训练、调试、采集或评估。

记录至少回答：

- 属于哪个实验、何时启动。
- 执行的是什么类型和配置。
- 当前状态是什么。
- 产生了哪些结果或为何失败。

实验中的“运行记录”可按类型筛选，不把某次采集的奖励显示成某次训练的收益。

### 某次运行详情

顶部始终显示实验名称、运行类型、时间、状态和配置快照标识。

根据运行类型展示适用内容：

| 内容 | 作用 |
| --- | --- |
| 概览 | 任务、配置摘要、状态与主要结果 |
| 训练曲线 | 本次训练的 loss、reward 等指标 |
| Rollout | 本次执行的轨迹、Agent 片段和工具交互 |
| 评估与诊断 | 检查结果、问题归因及相关证据 |
| 日志与产物 | 执行日志、模型产物、数据及下载 |

没有训练的调试记录不显示空训练曲线；没有评估的运行显示“未执行评估”，不展示零分。

运行详情中的内容必须属于当前选中的运行。找不到可靠归属的数据，不混入一张貌似完整的曲线。

### Harness 的位置

“配置检查规则”位于实验设置，“查看检查发现”位于运行详情。

诊断可以服务训练，也可以服务 MAS 调试。建议应关联实际证据；若未来支持自动修复，应先形成可审阅的修改，不直接覆盖当前画布或正在运行的配置。

## 十、独立采集与评估：保留能力，降低入口优先级

平台以训练为主目标，但 MAS 可以独立执行。

数据集采集放在“数据与采样”的对应操作中，评估放在评估配置或已有运行的明确操作中。执行时说明输入和目标，形成独立运行记录。

它们不占据调试面板的默认输入区域，不与主工作栏的“开始训练”争夺同一层级。

专业用户需要 Rollout 数据时，可以从对应入口采集、查看和导出；普通用户不必先理解数据生产接口才能调试一个问题。

## 十一、状态与问题如何呈现

### 按当前任务给出提示

| 用户正在做什么 | 此时需要看到什么 |
| --- | --- |
| 编辑 MAS | 保存状态、局部结构问题 |
| 配置模型 | 连接与凭据问题 |
| 发送调试 | 本次推理必要条件和执行反馈 |
| 开始训练 | 策略、数据和训练环境的阻断项 |
| 查看运行 | 该次运行的状态、结果和错误 |

不在编辑画布时常驻展示 `idle`、空 reward、AGL 离线或无关依赖清单。

### 信息分层

先给一句能理解的结论，再给解决操作，最后提供技术详情。例如：

> 暂不能调试：尚未配置模型凭据，执行环境也需要准备。  
> 配置模型 · 准备环境 · 查看详情

- 同一个问题只出现一次，不同时在告警、依赖列表和底部状态栏重复。
- 缺少 Python 包等内容放到技术详情，不作为正式产品首屏的主体。
- 状态必须准确区分未配置、未检查、可访问、执行失败和结果未知。
- 不支持模型列表探测不等于无法推理；调试成功不等于训练可用。
- 部分轨迹缺失如实说明，不推测执行过程，不用“全部正常”遮盖未知信息。

## 十二、视觉与交互原则

- **画布优先**：减少全局导航占位与无关标题，让工作对象可见。
- **上下文优先**：编辑节点时配置节点，开始训练时检查训练，查看结果时展示该次结果。
- **主操作唯一突出**：实验首页突出新建，工作区突出开始训练；辅助动作保持克制。
- **资源复用**：通过名称和引用选择模型、数据，避免重复输入底层配置。
- **渐进展开**：简单路径先可用，高级研究参数 和原始记录按需打开。
- **状态可区分**：草稿与运行、配置与实际执行、未评估与低分分别表达。
- **操作可预期**：查看不触发执行，选择历史不覆盖草稿，配置变化不修改已启动任务。

- **科学表达可信**：不把静态连线动画当作实际执行，不把模型名称当作训练能力，不把日志摘要当作完整轨迹。

## 最终用户心智

用户不需要沿着 LLM → MAS → RL → Harness → Monitor 逐页理解系统内部架构。

用户只需要形成一条清楚的工作路径：

**找到我的实验 → 在画布上设计 MAS → 选择资源 → 调试任务 → 配置训练 → 开始训练 → 查看这次运行的结果 → 根据证据改进设计。**

底层仍保持分层与独立接口，但产品围绕研究工作组织，而不是围绕代码模块组织。
