# Plan

> **状态：历史实施记录。** 本文记录从“首次 Tool 前缀”修到“每个 Tool Window 独立前缀”的既有工作，不再作为后续架构主路线。当前权威路线见 [Sampling 框架实施总览](Sampling框架实施总览.md)；本文成果作为 [S0 窗口合同与适配器核心](Sampling框架第一阶段-窗口合同与适配器核心.md) 和 [S1 ARPO Tool Result Window 适配](Sampling框架第二阶段-ARPO工具窗口适配.md) 的输入。

本阶段先使 Branch Site 的声明与训练行为一致：每个可启用站点必须对应真实执行事件、该事件自己的可恢复前缀和可求值的 Gate。先兑现 Tool 返回后的分支，再按实际事件能力逐步开放其他窗口；不先改六种 RL 算法，也不先重画 UI。

依赖现有训练快照和 `workflow.sampling`。后续依次实施[第二阶段：采样画布与策略编辑](采样编排第二阶段-画布与策略编辑.md)、[第三阶段：按 run 存储 Rollout Tree](RolloutTree第一阶段-按run存储与结果回填.md)和[第四阶段：树详情与实时更新](RolloutTree第二阶段-节点详情与实时更新.md)。本文与 [new_framework 设计](../../docs/NEW_FRAMEWORK_DESIGN.md) §2.3、[现有 ARPO 恢复方案](../../docs/NEW_FRAMEWORK_MIGRATION_PLAN.md)分开验收。

## Position in the Project

`workflow.sampling` 是声明源；`WindowEndEvent` 是位置证据；Archive 的快照是续跑源；`ForkPlan` 才能交给 Daemon enqueue。UI 中的角标和启动检查都必须由同一套已解析站点产生，不得分别推算。

```text
已保存 Workflow → 有效 Sampling / 站点解析
实际窗口事件 + 对应 Archive 快照 → 精确匹配 Site → Gate / 次数 / 预算
                                      → ForkPlan(站点, 事件, 前缀) → Store enqueue
```

## Concrete Example

ARPO 的执行形态不变：先跑 `initial_rollouts` 条父轨迹；每条父轨迹记录潜在分支窗口，随后对选中的站点判断 Gate 和剩余候选预算；通过后由 Daemon 入队子 rollout，让它共享**选中窗口之前**的消息并重新采样后续路径。不要求 Tool 返回时同步启动子任务，也不修改 GRPO/ARPO 的训练计算。

假设一条父轨迹先得到 Tool A 的结果，再得到 Tool B 的结果：

```text
父轨迹：问题 → A 返回 → B 返回 → 原答案
Site A 应用的前缀：问题 → A 返回             → 重新采样后续
Site B 应用的前缀：问题 → A 返回 → B 返回    → 重新采样后续
```

当前代码虽然能记录 A、B 的 Tool 事件，但 `branch_messages` 只在首次 Tool 返回时确定；后续窗口快照和 `ForkPlan.resume_messages` 仍可能取这份 A 前缀。若 Site B 的 Gate 通过，子任务标着“从 B 分支”，实际却从 A 后面继续。本阶段修的是**站点选择 → 真实事件 → 该事件的前缀 → Gate → 子任务**的一一对应，不是修复已有 ARPO 是否能够从首次 Tool 分支。

## Requirements

- 旧 `barriers: [after_tool]` 在没有显式 sites 时仍表示一个通用的首次 Tool 站点；显式 `barriers: []` 且 `sites: []` 表示没有站点。不能把前者在 UI 中显示为每个 Tool 都已单独启用。
- 显式 Site 的 `agent_id`、`tool_id` 与实际事件严格匹配；事件缺少被要求的身份字段时不视为命中。
- 每次命中携带稳定事件身份、实际 Tool/Agent、对应消息前缀及可恢复的 Archive 引用；不能把首次 Tool 前缀用于后续窗口。
- `first` / `every` / `nth` 对真实事件逐次计数；先匹配站点和次数，再计算该窗口的 Gate、探针和预算。
- 训练路径不能把缺少 `tool_ok`、`verifier_ok`、`final_failed` 等必要信号的 Gate 当作通过；UI 和启动检查明确报告能力缺口。
- 只有已实现真实事件与续跑快照的位置才能被标为“可执行”。现有不支持位置的 YAML 必须能读取和无损保存，但启动新的训练时明确阻断其启用状态；不改写旧运行快照。
- Control 预检、启动快照和训练脚本解析相同的有效站点及候选数；现有 ARPO 实验的显式站点不能因收紧语义而无提示失效。

## Scope

- In：站点解析、真实事件与快照配对、Gate 信号和次数规则、启动前站点能力检查、无 GPU 契约测试。
- In：先证明同一轨迹的两次 Tool 返回可以各自产生不同可恢复前缀；第二阶段再开放相应交互。
- Out：实现 token-prefix 分支、任意 Router/边/Verifier 的假事件、重写 VERL/AGL、改变六算法 advantage/loss。
- Out：将 Collect/mock 的多条独立 Rollout 冒充训练分支。

## Current State

- `SamplingSettings.tsx` 用 `effectiveSites()` 将 `barriers` 派生成逐 Tool 的显示站点；训练的字典路径在 `rl/hooks/overlay.py` 仅转发 `sites`，空列表进入 `ActiveSetSession._sites()` 后回退成一个泛化的 `after_tool`。`training.py` 的站点计数取显式列表，可能与两端都不一致。
- 上一项只针对没有显式 `sites` 的 legacy barrier；仓库的 `experiments/arpo_e2e/workflow.yaml` 实际声明了 `after_tool(hub, execute_python)` 和 `after_agent_turn(hub)` 两个站点。后者当前通过 `gates.py` 的 `after_tool`/`after_agent_turn` 兼容匹配命中 Tool 事件，并不证明 Hub 整个工作窗口结束时有独立可恢复边界。
- `mas/tir_agent.py` 已发出 Tool 边界事件，但后续 `window_snapshots[].messages` 仍可复用首次 `branch_messages`；`active_set.py` 对不同站点统一使用首次前缀。
- `gates.site_matches_event()` 在 `window_events` 非空时直接返回事件是否匹配，不执行其后的 `when` 计数判断；身份字段不存在时也可能匹配指定身份的 Site。
- UI 可选的 Router、`sample_barrier` 和部分 Gate 尚无对应训练事件/信号；`mas/workflow/compiler.py` 目前将 `sample_barrier` 仅作声明。
- `Archive.snapshot()` 可保存实际消息前缀，但事件里的 `snapshot_ref` 当前只是类似 `hub:0` 的位置标记，并非可独立恢复的 Archive 引用。

## Proposed Architecture

### 站点解析与能力

建立纯配置解析入口，分别返回 `declared_sites`、`effective_sites` 和逐项诊断。只按现有 YAML 显式声明和 legacy barrier 规则解析，不依赖 UI 当前画布中有多少 Tool。版本化的能力矩阵至少区分：首次 Tool、同一 Tool 的后续命中、Agent 窗口、Verifier、Router/边、token；每项写明事件、快照、Gate 信号是否具备。旧数据不因新增字段被重写；对不能执行的已启用站点，Preflight 给出站点 ID 与缺失条件并阻断启动，而非静默退化。

### 事件与前缀

在实际可恢复的 Tool 边界记录该次完整消息前缀，由 Archive 产生可恢复引用；事件绑定 `rollout_id`、Agent/Tool、顺序、对应引用及可用的窗口指标。不要将含凭据或原始消息的快照内联进 Control 预检、树事件或公开 API。`plan_forks_from_raw()` 遍历真实事件，按所选事件取对应前缀及 GateContext，按 Site 和事件身份计数；没有快照时不生成 ForkPlan。兼容旧数据的自匹配只允许保留既有单一 legacy `after_tool` 行为，不用来使新显式 Site 假阳性通过。

现有实验中明确依赖 `after_agent_turn(hub)` 的兼容别名先保留并如实标为“Hub 内 Tool 边界”，不能静默重解释为 Agent 完成后；真正的 Agent、Verifier、Router/边站点必须等运行时发出各自边界事件并能恢复对应前缀后才逐项启用。`on_token` 按设计文档属于暂不做的窗口内能力，不增加虚假的可用开关。

## Implementation Notes

- `SamplePolicy.resolved_sites()` 成为配置解析入口；字典和模型形式的 Workflow Sampling 现在通过同一规则写入 `algorithm.tir.sites`。显式 sites（包括全部禁用）不再回退 legacy barrier；没有 Workflow Sampling 的旧 CLI 入口仍使用默认首次 Tool 语义。
- 页面不再把通用 legacy barrier 绘成逐 Tool 启用的站点；具体 Tool Site 只在用户显式开启后物化。Preflight 使用最终站点数，并对缺事件或缺信号的声明给出站点级阻断，对现有 `after_agent_turn(hub)` 的 Tool 边界兼容别名给出警告。
- Runner 在实际 Tool 边界保存当时的 messages，下一次模型响应再给该事件补上用于 Gate 的熵指标；训练父 rollout 为各窗口写独立 Archive 快照。Planner 逐个匹配事件和站点，从该事件的前缀计算 Gate 并生成 ForkPlan；Daemon 继续通过原有 Store 两波入队，不改算法更新。
- 本轮未新增测试用例或启动真实 GPU 训练。Python 编译和 WebUI 构建仅覆盖代码接线；站点命中、前缀及显存/进程行为仍须用户在服务器手动确认。

## Lightweight Validation

使用纯配置、mock WindowEndEvent 和可恢复 Archive fixture，核对相同 Tool 的第一次/第二次与两个不同 Tool 的前缀、`first/every/nth`、缺失身份和 Gate 信号、空站点与旧 barrier。仅做 Python 轻量检查；真实 GPU 训练必须由用户在服务器上明确启动。

## Acceptance and Delivery Boundary

- 只有 legacy barrier、没有显式 sites 的实验在 UI、Preflight、快照及执行端都只算一个通用站点；`arpo_e2e` 的两个显式站点保持可见，并如实解释其中 `after_agent_turn(hub)` 的兼容边界语义。
- 同一任务两个受支持边界的 Site 分别记录真实事件与不同可恢复前缀；子 rollout 从选定前缀继续，不共享首次 Tool 的消息。
- 不支持的显式站点在保存后仍可回显，但 Preflight 明示原因且不允许假执行。
- 这只是可执行采样合同，不表示 Router/Verifier/token 都已可分支，也不表示六种算法已验收。

## Risks and Edge Cases

- 真实事件流中一个站点可能多次命中；计数不能以每条 episode 或每次调用 `plan_forks_from_raw()` 代替。
- Archive 快照可能包含私有消息；公开摘要只能给身份与脱敏指标，不返回原始前缀。
- Tool 无返回或边界不能恢复时应明确不创建子任务；不能以完整 episode 的末尾消息假装可中途恢复。
