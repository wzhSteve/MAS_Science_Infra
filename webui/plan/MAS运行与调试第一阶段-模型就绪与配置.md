# Plan

本阶段定位为“模型接入与最小执行契约”，是面向 RL 的 MAS 执行与 Rollout 层的第一步。先以远程 API 作为模型来源，建立后续可由自部署模型或训练策略复用的配置、执行输入和记录边界，不另建一套将来需要废弃的聊天调试系统。

使用远程 OpenAI 兼容 API 时，可以在本机没有显卡、不启动 RL 训练的情况下完成 Workflow rollout。本机运行编排、工具和轨迹记录，模型推理由远端 API 服务承担。若使用本地模型或需要 GPU 的自定义工具，则对应服务仍需自己的算力，不能把“MAS 不需要训练 GPU”理解成所有执行方式都不需要 GPU。

本阶段的实现进度见 Action Items。模型接入和契约定义不等于已执行真实 Rollout；实施过程中不自动发起付费探测或训练。

## Position in the Project

项目目标是通过可视化画布定义 MAS，并让其产生可以被采样策略、评估器和学习更新模块消费的轨迹。四层是职责划分，不是四个必须按顺序执行的页面：

```text
MAS 定义：参与者、协作关系、工具
                   ↓
采样策略：选择任务、次数、分支位置与预算
                   ↓ 调用
执行与 Rollout：给定任务、Workflow 和模型，执行并记录
                   ↓ 返回
采样策略：决定是否继续采样或分支
                   ↓
评估与学习：奖励、优势、损失、模型更新
                   ↓
更新后的策略进入下一轮采样
```

本次三个阶段只建设其中“执行与 Rollout”的首期基础能力。一个任务从入口运行一次、不分支，就是首期最小采样方式；不必先实现 ARPO 或启动训练。

- API 模型也是真实推理，不把它与“真实模型”对立；正确区分是远程服务、自部署服务、训练过程提供的策略。
- 替换的是模型接入与资源来源，不能因此替换 MAS 编排语义或轨迹格式。
- UI、批量 Collector 和训练 worker 可以有不同入口，但必须复用执行核心，不要求都经过浏览器或同一 HTTP 路由。
- “独立于 RL 运行”表示不强制启动学习更新，不表示放弃记录训练需要的身份与来源信息。
- 现有 Collect 是“执行 + 奖励 + 训练信号包装”的组合入口，不是废弃功能，后文统一称“现有采集入口”。

## Requirements

- MAS 远程 API 运行不依赖本机 GPU、VERL 或 Agent-Lightning 训练服务。
- 模型配置是执行输入；远程 API 不依赖 RL 配置，训练入口则可显式注入策略端点、采样参数和已有 trace 上下文。
- 区分 Agent 身份和模型 / 策略身份：多个 Agent 可以共享一个模型，不要求每个节点独立加载权重。
- 首期定义最小 Agent 契约，复用现有 Prompt、Skill、工具、MemoryStore 和 Archive，不先构建完整 Agent 平台。
- 区分配置完整、本地依赖可用、端点可访问、鉴权有效、实际推理成功和工具调用兼容性。
- 页面加载时只做本地就绪检查，不自动发送模型生成请求或工具调用。
- “未探测”不是失败，“端点可访问”也不等于模型已可以执行 Workflow。
- mock 不依赖 API Key、远端模型或 live 执行依赖。
- 模型密钥只在服务端解析和使用，不回显、不进入运行快照或错误日志。
- 在现有 LLM 页面修改配置；MAS 控制台显示摘要和跳转入口，不复制第二套模型表单。
- 不因本地没有显卡或 AGL 离线阻止远程 API 运行。
- 不把缺失依赖静默切换为 mock，真实运行失败必须明确报告。

## Scope

- In：模型就绪状态、LLM 配置保存语义、连接探测修正、live 可选依赖、请求级凭据传递、控制台模型摘要。
- In：`api`、`local`、`rl_endpoint` 三种来源在独立 MAS 运行中的边界说明。
- In：最小执行输入、模型返回能力和 Rollout 记录契约；实际调用边界的记录接线在第二阶段完成。
- Out：单题输入、新调试执行 API、轨迹详情、训练参数改版、安装 GPU 推理栈。
- Out：全供应商适配、Agent 级独立模型配置、自动尝试多个模型或自动重试付费请求。
- Out：将现有 Python 执行核心重写为 TypeScript、完整 pi 类 Agent 系统、长期记忆平台。

## Current State

以下为本阶段实施前的基线；已落地的变化见 Implementation Notes。

- `LLMPanel` 已提供 API、Local、RL endpoint 三种配置模式。
- `run_collect()` 从实验配置读取端点和模型，调用 `Collector`，没有调用 `start_train()`。
- `Collector` 和 `ExecutionService` 不要求 VERL 或 Agent-Lightning 训练进程。
- 根目录 `pyproject.toml` 已有 `live` 可选依赖；parquet 依赖不应成为单题 API 调试的前置条件。
- 当前 `llm_health()` 请求 `/models`，采用 `status_code < 500` 判断成功，会把部分鉴权失败或限流误报为健康。
- 连接探测与真实运行对密钥的读取路径不完全一致；清空输入框后不能假设保存的实验密钥会被正确用于探测。
- `api_key_set` 当前仅反映环境变量或 sidecar 文件存在，文件存在并不证明其中有有效密钥。
- `_llm_env()` 的结果被写入进程级 `os.environ`，共享后端的不同实验可能相互影响。
- TirAgent 目前从环境读取密钥，尚无完整的请求级凭据传递。
- `rl_endpoint` 已有“独立 Collect 不可用”的前端说明，但不能仅依靠说明阻止误用。
- `LLMConfig`、`EpisodeRunner`、`MemoryStore`、Skill 注册表与 Archive 已存在，优先完善它们的职责边界。
- 当前部分 Skill 和内存记录围绕 hub 实现，不能假设每个画布 Agent 的配置都已经完整生效。
- 训练侧 `LitTirAgent.rollout()` 与 Control 侧 `ExecutionService` 的调用路径不完全一致；第二阶段应统一 MAS 执行分派，不能只换模型地址就宣称训练也按相同 Workflow 运行。

环境调查只能说明调查时的依赖状态。实施时应以实际运行 Control 服务的解释器为准，不能把某个终端能 import 包当成服务依赖已满足。

## Proposed Architecture

```text
LLM 页面保存配置
  → 服务端解析当前实验的有效模型配置
  → MAS 控制台读取脱敏摘要与本地就绪状态
  → 用户按需触发端点探测
  → 实际运行继续复用同一配置解析结果
```

建议在 `science_infra\control` 内提取小型模型配置解析模块：

- 集中解析模式、端点、模型和密钥来源。
- 公开摘要与内部执行配置分开，内部配置不允许直接序列化返回。
- 就绪检查、端点探测、现有采集入口和单次 Rollout 入口使用同一解析规则。
- 密钥优先级明确为：本次显式探测输入 → 当前实验保存的密钥 → 服务启动时解析的环境 / 仓库配置。
- 普通运行没有前端临时密钥覆盖，只使用已保存配置及明确的服务端默认来源。
- 传给子进程的环境副本可以保留；当前进程的独立推理应显式传递凭据，而不是每次修改全局环境。
- 为 `LLMConfig`、TirRunner 和 TirAgent 补充可选的请求级凭据传递，兼容现有 CLI / 训练调用的默认行为。
- 同一配置解析过程完成后生成快照，单次运行中不因其他实验保存配置而切换模型。

不引入通用 provider 框架；本阶段仍以现有 OpenAI 兼容协议为主。

## Model Boundary and Implementation Language

从 MAS 的推理调用侧，远程 API 与自部署模型可以看作同一契约的不同实现，甚至使用完全相同的 HTTP 协议。训练中的模型还需要资源管理、策略版本和权重更新边界，不能简化成“只有一个地址不同”。

```text
服务端 MAS 执行器（当前 Python；原则上也可为 TypeScript）
  → 推理接口：上下文、工具定义、采样参数
  ← 可见输出、工具请求、结束原因、可用的 token/logprob/usage
  → 统一 Rollout 记录
  → 训练适配器 / 评估器（通常 Python）
```

- MAS 执行器不必与模型或优化器使用同一种语言，跨语言通过有版本的结构化契约协作。
- 浏览器 TypeScript 负责配置与呈现；若未来用 TypeScript 执行 MAS，应部署在可信的服务端 worker，不能让浏览器持有密钥并承载可靠采集。
- 当前已有 Python MAS 核心、Archive 和训练适配器，本阶段复用它们，语言迁移不解决眼下的轨迹记录问题。
- 第一版所有 Agent 可继承同一模型绑定，但每次调用仍记录各自 Agent 身份与实际模型身份。
- 策略版本、token IDs、logprobs、tokenizer 标识等有则保留，未知则明确标记；模型名字相同不代表同一策略版本。
- API 轨迹并不天然是另一个模型的 on-policy 样本。训练端仍负责算法所需的数据对齐、奖励、优势与优化，普通对话 JSON 不自动等价于完整 RL 训练数据。

## Minimal Agent Execution Contract

本阶段先定义契约，第二阶段把它接到真实执行边界，不要求建设完整 Agent 操作系统。

| 能力 | 首期必需的约定 | 暂不建设 |
| --- | --- | --- |
| Prompt | 每个 Agent 实际生效的系统提示词可确定、可记录 | Prompt 管理平台 |
| 上下文 | 任务输入、上游交接、历史消息以及实际发送前的裁剪结果可追踪 | 通用长上下文治理平台 |
| 记忆 | 运行内 Agent 私有状态按 owner 隔离；共享状态只通过明确机制读写 | 向量检索、长期记忆、跨会话自动学习 |
| Skill | 定义调用时机、输入、结果、错误及记录事件；声明的能力不能静默忽略 | Skill 安装市场与全格式兼容 |
| Tool | 显式可用集合、参数、调用 ID、返回和异常 | 新的工具平台 |
| 执行循环 | 明确 Agent 进入、模型请求、工具返回、交接与终止边界 | 通用自治 Agent 框架 |
| Recorder | 记录实际 Agent、执行片段、模型调用、工具调用及错误 | 独立 tracing 平台 |

- Skill 当前是代码注册的执行接口，不自动等于 Markdown 提示词片段；应按现有机制解释并接线。
- 不能仅保存 Workflow 上声明的 Prompt / Skills，必须能说明本次实际使用了什么。
- 初始上下文和 MemoryStore 每次运行默认重新创建；不允许不同任务或实验意外共享状态。
- 参考答案和评估数据与模型可见上下文分开，不能为评分方便泄漏到模型输入。
- 快照记录其可恢复范围：只有消息快照就标明仅含消息，不能承诺任意多 Agent 状态续跑。
- 最小训练归属元数据从首期保留：哪个 Agent、哪次调用、哪个模型；复杂算法字段和完整恢复协议不提前实现。

## Readiness Model

| 检查项 | 结果与含义 | 是否阻止开始真实运行 |
| --- | --- | --- |
| 配置模式 | API / Local / 训练注入 | 未有运行时资源注入的训练模式阻止独立 UI 运行，不禁止训练适配器显式注入 |
| 端点与模型 | 未填写 / 已填写 | 缺失时阻止 |
| live 依赖 | 可用 / 缺失 / 导入失败 | 不可用时阻止真实运行，不阻止 mock |
| 密钥来源 | 实验配置 / 服务默认 / 未提供 | 未提供给出提示；无鉴权兼容服务不应被一律禁止 |
| 端点探测 | 未探测 / 可访问 / 鉴权失败 / 限流 / 网络失败 / 不支持模型列表 | 作为诊断证据；不把不支持 `/models` 等同于不支持推理 |
| 工具兼容性 | 未确认 / 最近真实请求成功 / 最近真实请求失败 | 不伪造静态能力结论，具体请求仍可能失败 |
| 采样数据能力 | token/logprob/策略版本可用、未知或不支持 | 不阻止基础 rollout；后续算法自行判断是否满足要求 |

建议新增只读 `/api/mas/readiness?experiment_id=...`：

- 只读取本地配置与依赖，不产生外部请求。
- 返回模式、模型、可展示的端点、密钥来源标记、依赖问题和修复指引。
- URL 中若含认证信息必须移除，不返回原始环境变量、密钥或 sidecar 内容。
- 区分 `blocking_issues` 与 `warnings`，避免前端重新推断阻断规则。
- 不把 GPU 数量或 AGL 状态纳入远程 API 运行的阻断项。

本接口以及后文新接口均为拟新增能力，不是现有接口。

## Connection Probe

修正现有 `/api/llm/health`，优先保持旧字段可兼容：

- 2xx 且响应符合预期才说明模型列表请求成功。
- 401 / 403 明确为鉴权或权限问题；429 明确为限流。
- 404 / 405 可表示供应商不支持模型列表，不宣称“无法推理”。
- DNS、TLS、连接超时和服务错误明确区分，不把错误包装成健康。
- 若用户未提供临时 Key，使用当前实验的有效凭据，不能误用上一实验的环境副作用。
- 探测结果标明探测类型、时间和对应的配置；端点、模型或凭据变更后将旧结果标为过期。
- 不自动发起 chat completion 检测。需要实际生成来确认兼容性时，引导用户进入第二阶段的明确执行操作。
- 工具调用成功需要真实工具调用证据，不能仅根据模型名称或 `/models` 返回推断。

## UI Layout

MAS 控制台增加轻量模型摘要，不新增永久大型表单：

```text
模型：当前模型名称 · 远程 API          配置模型
本机无需显卡
就绪状态：配置完整 / 缺少执行依赖 / 待探测
```

- 初次进入只展示必要摘要，问题出现时展开修复说明。
- 缺少依赖时说明应在哪个服务环境安装，不在浏览器提供任意安装命令执行按钮。
- 点击“配置模型”切换现有 LLM 页面，保持当前 Workflow 和运行输入草稿。
- LLM 保存成功后刷新就绪摘要；探测不保存配置，保存也不自动探测。
- Local 模式必须有可用模型服务；“不需训练”不代表自动启动本地模型。
- RL endpoint 模式提示“此模式由训练过程注入，独立运行请选择 API 或本地服务”。
- 训练资源信息留在训练区域，不让“无 GPU”或“AGL 离线”占据 API 调试主视图。

## Dependency Strategy

- 复用 `pyproject.toml` 的 `live` extra；需要调整时只补齐实际执行导入链所需依赖。
- 不为 API 调试安装 torch、CUDA、VERL 或完整训练栈。
- parquet 支持按数据集功能单独说明，pandas 与 parquet 引擎不阻塞单题文本输入。
- 检查真实执行模块能否导入并报告明确缺失项，不仅检查模块名称是否存在。
- 就绪接口不频繁反复执行重量级 import；依赖状态在服务生命周期内缓存，环境变化后重启服务或显式刷新。
- 不硬编码某台机器上的 Python 路径，文档以“启动 Control 的解释器 / 虚拟环境”表述。

## Implementation Notes

- `EffectiveLlmConfig` 固定一次请求的模型与凭据，公开摘要不含 Key；服务默认配置在模块初始化时捕获。Collector 通过显式 `LLMConfig` 传给 TirAgent，不再逐次修改进程环境。
- `LLMConfig.api_key=None` 保持 CLI / 训练原有默认解析；Control 明确传入字符串，空字符串不会继承其他实验的密钥。
- 就绪接口返回 `ready`、阻断 / 提示项、live / parquet 依赖、能力未知状态和仍对应当前配置的最后一次探测。依赖结果缓存至服务重启。
- `pyproject.toml` 增加独立的 `data` extra；没有 parquet 引擎不阻断普通 live 示例任务，没有 live 依赖不阻断 mock 示例任务。
- 端点保存时拒绝嵌入认证信息、查询参数和片段；公开端点也会去除这些内容。模型列表探测不跟随重定向、不回传供应商原始错误体，不将可访问误报为生成成功。
- `config_revision` 是服务内 HMAC 标识，包含配置与凭据来源；配置或凭据变化使旧探测失效，不对外暴露可猜测的密钥摘要。
- `llm.yaml` 是 Control 模型配置的权威来源。Workflow 保存保留其当前模型绑定，防止画布旧草稿反向覆盖 LLM 页面刚保存的配置。
- MAS 通过 `useModelReadiness` 按实验、配置版本与返回页面时刷新本地就绪信息；“配置模型”切换既有 LLM 面板，不卸载 MAS 草稿和运行输入。
- LLM 页面只手动探测，结果关联本次提交的输入与配置版本；编辑或保存不同配置后标记旧探测过期。保存返回不会清空用户在等待期间重新输入的 Key。
- 控制台分别限制 live 和 parquet 所需条件，mock 示例仍可独立运行；模型与工具能力保持“尚未验证”的真实表述。
- 最小契约为 `AgentExecutionContext`、`ModelIdentity`、`ModelCapabilities`、`ExecutionRecorder` 和 `SnapshotCoverage`；事件新增的执行 / 调用归属字段均可选。它们定义第二阶段的接线边界，不宣称已完成细粒度 Rollout 采集。
- 本阶段不统一训练 worker 的 MAS 分派，也不实现单次 Rollout 新接口；相关工作继续留在第二阶段。

## Delivery Boundary

本阶段交付“模型接入可信 + 最小执行与记录契约明确”，不宣称已完成一次真实 rollout，也不宣称更换端点就已具备完整 RL 训练能力。模型未实际调用前，界面只能说明可尝试运行，不能显示“推理已验证成功”。

不设置测试用例或自动化测试阶段。实现时保证前端 TypeScript / Vite 编译和后端模块导入正常；外部模型请求必须由用户明确触发。

## Risks and Edge Cases

- 无鉴权的兼容 API 不能被统一的“必须填写 Key”规则误阻断。
- 供应商不支持模型列表与鉴权失败是不同情况。
- 旧配置与新的显式凭据传递必须兼容，但不能继续保留跨实验密钥串用。
- 服务默认配置只作为明确默认来源，不从某次请求污染的环境中继承。
- API 能生成文本但不支持工具调用时，应明确兼容失败，不降级为虚假的工具执行。
- 当前默认 Prompt 对部分任务要求调用工具；是否调用还受 Prompt 影响，不能把“按需绑定”解释为绝不约束工具使用。
