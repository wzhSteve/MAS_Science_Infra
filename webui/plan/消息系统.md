当前问题确实存在：WebUI 中约 **40 个文件使用 `InlineNotice`**，操作结果、字段错误、页面加载失败、运行异常和配置说明都使用了相同的页面内提示；同时还有多处 `window.confirm`。信息没有按照用户是否需要立即处理、是否长期存在、是否阻断操作来分类。

但不应该把所有错误都改成悬浮通知。合理方案是建立统一的 **Feedback System**，将信息分成四种承载方式。

## 一、信息展示规则

| 类型 | 适用场景 | 展示方式 |
|---|---|---|
| 短暂操作反馈 | 保存成功、复制成功、启动请求已提交、刷新完成 | Toast 浮动通知 |
| 操作失败 | 保存失败、启动失败、停止失败、删除失败 | Sticky Toast，手动关闭，可带“重试/查看日志” |
| 持续页面状态 | 模型未就绪、训练配置缺失、列表加载失败、运行中断 | 页面内 `InlineNotice` |
| 需要用户决定 | 删除、停止训练、放弃草稿、保存后启动 | Modal 确认对话框 |
| 轻量状态 | 已保存、运行中、未配置、GPU 状态 | Badge / 状态文字 |
| 页面无法工作 | 实验不存在、页面渲染异常、核心数据无法加载 | 页面级错误状态 |

判断原则：

> **操作产生的结果用 Toast；内容自身存在的问题留在内容旁边；需要决定的事情使用 Dialog。**

因此，大部分当前的保存、启动、停止、复制等操作反馈都应该从页面中移到 Toast，但配置错误、训练失败详情和就绪检查不能只用 3 秒后消失的通知。

## 二、统一通知模块

建议新增：

```text
shared/feedback/
├── NotificationProvider.tsx
├── NotificationViewport.tsx
├── NotificationItem.tsx
├── notificationStore.ts
├── useNotify.ts
├── ConfirmProvider.tsx
├── useConfirm.ts
└── types.ts
```

使用已有的 `radix-ui` Toast 和 AlertDialog，不增加依赖。

### 通知数据结构

```ts
type NotificationTone = 'success' | 'info' | 'warning' | 'danger';

interface NotificationInput {
  title?: string;
  message: string;
  tone: NotificationTone;
  duration?: number | null;
  dedupeKey?: string;
  action?: {
    label: string;
    run: () => void;
  };
}
```

调用方式：

```ts
const notify = useNotify();

notify.success('实验已保存');
notify.info('训练进程已启动', {
  action: { label: '查看日志', run: () => viewTraining(runId) },
});
notify.error('训练停止失败', {
  persistent: true,
  action: { label: '重试', run: retryStop },
});
```

业务组件不应该自己控制通知位置、动画、定时器和颜色。

## 三、Toast 的产品行为

### 生命周期

| 类型 | 默认行为 |
|---|---|
| Success | 3 秒自动消失 |
| Info | 4 秒自动消失 |
| Warning | 6 秒；有操作按钮时不自动消失 |
| Danger | 默认不自动消失，用户关闭或完成操作后消失 |

统一支持：

- 点击通知空白区域关闭。
- 右上角关闭按钮。
- 悬停、键盘聚焦时暂停计时。
- 有“重试”“查看日志”等操作时，点击操作不触发卡片关闭逻辑。
- `Escape` 关闭当前通知。
- 浏览器切到后台时暂停倒计时。
- 最多同时显示 3 条，其余排队。
- 相同 `dedupeKey` 更新已有通知，不重复堆叠。

例如 GPU 每 10 秒探测失败，不能每次新增一条：

```ts
notify.warning('GPU 状态暂时不可用', {
  dedupeKey: 'gpu-poll-error',
});
```

重复错误可以显示 `重复 3 次`，恢复后主动移除该通知。

### 视觉布局

```text
┌──────────────────────────────┐
│ ✓ 实验已保存             ×  │
│   arpo_e2e 的修改已写入      │
└──────────────────────────────┘
```

- 桌面端位于右上角、唯一顶栏下方。
- 宽度约 360–400px。
- 不使用大面积高饱和红绿背景，只用浅背景、图标和左侧状态色。
- 移入/移出动画控制在 150–200ms。
- `prefers-reduced-motion` 时关闭位移动画。
- 移动端占左右 12px，不覆盖关键操作。
- Toast 层级高于普通面板，低于阻断式 Dialog。

## 四、确认对话框统一替换 `window.confirm`

当前停止训练、删除资源、放弃草稿、清除密钥等操作仍在使用浏览器原生确认框。应统一为：

```ts
const confirm = useConfirm();

const accepted = await confirm({
  title: '停止训练？',
  description: `将停止运行 ${runId} 及其子进程。`,
  confirmLabel: '停止训练',
  tone: 'danger',
});
```

对话框类型只需要三种：

1. **普通确认**：应用资源建议、切换凭据方式。
2. **危险确认**：删除资源、停止训练、解除绑定。
3. **未保存修改**：放弃、保存后继续、取消。

训练 Preflight 和导航保护继续使用专用 Dialog，因为内容复杂，不应强行塞入通用 Toast。

## 五、`useAction` 的改造

现在 `useAction` 将结果保存在组件本地 `notice` 中，导致每个页面重复渲染 `InlineNotice`。建议支持统一反馈策略：

```ts
const action = useAction({
  feedback: 'toast',
  successMessage: '实验已保存',
});
```

或者操作动态返回：

```ts
await action.run('save', async () => {
  await saveExperiment();
  return {
    message: '实验已保存',
    tone: 'success',
  };
});
```

建议规则：

- mutation 默认使用 Toast。
- query/load 默认不自动 Toast，由页面决定是否需要持续错误状态。
- 组件仍可选择 `feedback: 'inline' | 'silent'`。
- `pending` 保留在组件内，因为按钮 loading 只影响当前操作。
- 通知状态不放在业务组件内。

这样不会让所有请求失败同时生成页面提示和 Toast，避免重复反馈。

## 六、当前内容的迁移分类

### 应改成 Toast

- `ExperimentHome.createdMessage`
- 保存实验、保存 RL、保存 Harness、保存模型资源成功
- 训练进程启动请求成功
- 停止请求成功或失败
- 复制日志成功或失败
- 导出、下载准备失败
- 数据资源创建、编辑失败
- 模型绑定保存失败
- 显式刷新失败但页面仍保留旧数据
- 后台训练从 running 转为 succeeded / failed

训练完成通知：

```text
训练已完成 · f5b98a9861a5
[查看日志]
```

训练失败使用持久 Toast：

```text
训练失败 · process
训练进程退出码 1
[查看日志] [关闭]
```

### 保留页面内提示

- 模型就绪检查及阻塞原因
- Workflow 不可执行
- 没有可训练 Agent
- 多 Agent 当前不受支持
- 训练 Preflight 检查项
- 数据集、模型资源列表读取失败
- 运行 `interrupted`
- 日志连接失败和重连按钮
- 节点、边配置错误
- 轨迹读取失败
- 表单字段校验错误
- 页面边界错误

这些信息与当前内容密切关联，Toast 消失后用户会失去定位。

### 改成 Dialog

- 停止训练
- 删除模型资源
- 清除密钥
- 放弃未保存内容
- 解除模型绑定
- 应用资源建议
- 保存配置并开始训练
- 跨实验导航

## 七、React 性能设计

通知 Provider 不能把通知数组直接作为 Context value，否则每次日志或通知变化都会让所有 `useNotify()` 消费者重渲染。

建议采用外部 store：

```ts
const notificationStore = {
  subscribe,
  getSnapshot,
  push,
  dismiss,
  update,
};
```

- Context 只提供稳定的 `push/dismiss` API。
- 只有 `NotificationViewport` 使用 `useSyncExternalStore` 订阅通知列表。
- 业务组件调用 `notify()` 不会因为其他通知变化而重新渲染。
- `NotificationItem` 使用 `memo`。
- ID、定时器和去重逻辑集中管理。
- 最多保留有限队列，防止长期轮询错误造成内存增长。
- 后台运行状态只在状态发生变化时通知，不因每次轮询重复通知。
- React 日志虚拟化和画布不会受到通知更新影响。

## 八、建议实施阶段

### 第一阶段：基础模块

- 建立 Notification Store、Provider、Viewport 和样式。
- 接入应用根节点。
- 建立 `useNotify`。
- 不迁移现有业务，先保证基础设施独立。

### 第二阶段：操作反馈迁移

- 改造 `useAction`。
- 迁移保存、启动、停止、复制、删除等操作。
- 删除对应页面里的成功/失败 `InlineNotice`。
- 同一个错误只能出现一次。

### 第三阶段：统一确认框

- 建立 Promise 风格 `useConfirm`。
- 替换所有 `window.confirm`。
- 保留训练 Preflight 和导航保护专用 Dialog。

### 第四阶段：运行事件通知

- 监听训练状态的真实迁移：
  - `running → succeeded`
  - `running → failed`
  - `running → cancelled`
- 首次加载已有历史状态不弹通知。
- 通知按钮打开准确 run ID 的日志。
- 对 GPU、日志连接等轮询错误做去重和恢复处理。

### 第五阶段：信息审计

逐项检查所有 `InlineNotice`：

- 操作结果迁到 Toast。
- 内容错误继续 inline。
- 可定位到字段的错误放到字段附近。
- 持续运行状态改为 Badge。
- 阻断操作改为 Dialog。
- 删除已废弃的 `TrainingBanner`、`StatusBar` 等重复反馈入口。

## 验收标准

- 保存、启动、停止等操作不再改变页面布局。
- 同一错误不会同时显示在页面和 Toast。
- Success 三秒自动消失。
- Danger 默认保留，支持重试和关闭。
- 轮询错误不会每次请求产生新通知。
- Dialog 支持焦点锁定和返回原触发按钮。
- 屏幕阅读器能正确区分普通通知和紧急错误。
- 通知更新不会触发画布、日志或训练配置表单重渲染。
- 训练失败通知能准确打开对应 run，而不是当前猜测的活动 run。

**核心方向不是“把所有 InlineNotice 改成弹窗”，而是建立统一反馈语义：Toast 负责短暂操作结果，InlineNotice 负责持续上下文问题，Dialog 负责用户决定，Badge 负责状态。**

## 第四、第五阶段实施记录

- `useTrainingRun` 只追踪当前会话真实观察到的活动 run。活动接口在终态变空后，继续按该 run ID 读取最终状态；首次加载历史终态不会弹通知。
- RuntimeProvider 仅在同一 run 从运行态迁移到终态时通知：完成、失败、取消、托管中断。通知操作直接打开准确 run ID 的日志；失败和中断保持 Sticky。
- GPU 十秒轮询失败使用实验级 `dedupeKey` 更新同一条 Sticky Warning，并提供重试；恢复后自动移除。GPU 下拉框保留设备状态，不重复显示同一错误正文。
- 日志连接失败继续保留在控制台上下文内，已有重连和增量回退，不同时弹 Toast。
- 全量审计后，操作结果已迁出页面布局；字段校验、配置阻塞、列表读取失败、模型就绪、轨迹读取、运行失败详情和 `interrupted` 等持续问题继续 inline。
- 删除未被引用的 `TrainingBanner`、`StatusBar`、`GlobalActionBar` 及对应样式；训练状态统一由顶栏、控制台和 Toast 承担。
- 训练失败不再同时出现在顶栏 InlineNotice 与 Toast；详细原因仍保留在对应 run 控制台。

五个阶段代码均已接入。后续仅需在服务器验证 Toast 视觉、确认框焦点、GPU 错误恢复和训练终态通知，不再新增信息承载体系。
