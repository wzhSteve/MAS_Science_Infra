# Plan

本阶段把已有 `services.start_train()` 和 `ProcessManager` 收敛为可靠的训练运行契约：每次启动拥有稳定身份和不可变配置快照，冲突不会自动替换已有任务，停止只作用于用户明确选择的运行。

依赖 [第一阶段：模型来源与启动前检查](训练运行第一阶段-模型来源与启动前检查.md)。本阶段保持 `mas/train_tir_agent.py`、Agent-Lightning 和 VERL 为实际训练入口，不在 Control 层重写训练循环。

## Position in the Project

Control 层负责命令、生命周期、快照和错误；`mas/train_tir_agent.py` 负责把有效配置交给 AGL/VERL；`rl/hooks/` 负责算法行为。三者不能混成一个 UI 请求处理函数。

```text
WebUI TrainCommand
  → Control 再次 Preflight
  → 创建 run + 固定有效配置
  → ProcessManager 启动进程组
  → mas/train_tir_agent.py
  → Agent-Lightning / VERL / rl/hooks
```

## Requirements

- 每次训练拥有稳定 `run_id`，启动响应直接返回该 ID。
- 启动前在服务端重新检查配置，前端 Preflight 只用于展示。
- Worker 读取本次运行快照，而不是运行中的可编辑实验 YAML。
- 同一 GPU 资源已有训练时返回冲突，不自动杀掉旧训练。
- 本地 vLLM 冲突必须在摘要中显示，并按用户确认结果停止。
- 停止接口按 `experiment_id + run_id` 校验归属。
- 停止覆盖完整进程组，正常中断超时后才升级强制终止。
- 状态明确区分准备、启动、运行、停止中、成功、失败和取消。
- 服务重启后能够读取历史终态；不能仅凭 PID 存活宣称旧任务仍是原训练。
- 启动错误和运行错误保留真实阶段与可读原因。
- 旧 `/api/rl/train` 和 `/api/rl/stop` 在迁移窗口内保持兼容，但新 UI 使用新契约。

## Scope

- In：训练运行记录、不可变快照、状态机、冲突检测、幂等保护和定向停止。
- In：进程 stdout/stderr 文件、结束状态和停止原因持久化。
- In：新训练 API 与旧接口适配。
- Out：实时日志传输和完整训练工作区，它们属于第三阶段。
- Out：修改 GRPO/ARPO 等算法计算，它们属于第四阶段。
- Out：多机调度、队列系统、跨节点恢复和通用作业编排平台。

## Current State

- `ProcessManager` 使用 `_by_kind[kind]` 保存单个活动进程，不按实验或 GPU 建模。
- `start(..., replace=True)` 会终止同类旧进程，可能无提示替换另一实验的训练。
- `stop_train(exp_id)` 实际调用 `PROCS.stop("train")`，没有使用传入的实验 ID 校验归属。
- 运行状态只有 `running` 和 `returncode`，前端无法区分启动失败、正常完成和用户取消。
- `status.json` 只在创建与结束时写入；服务重启后主要依靠 PID 是否存在推断运行状态，存在 PID 重用风险。
- 训练直接读取实验目录内的 `rl.yaml` 和相邻 `workflow.yaml`，运行期间继续编辑可能改变尚未加载的配置语义。
- `start_train()` 已能同步 GPU、Sampling、算法、模型参数和可训练 Agent，但缺少统一快照边界。

## Proposed Architecture

### Run Record

新增明确的训练运行记录：

```text
experiments/<id>/artifacts/runs/<run_id>/
├── status.json
├── launch.json
├── effective-rl.yaml
├── effective-workflow.yaml
├── stdout.log
└── events.jsonl
```

状态机：

```text
preparing → starting → running → succeeded
                         ├─────→ failed
                         └─────→ stopping → cancelled
```

`status.json` 至少包含：

```text
run_id
experiment_id
kind
state
pid / process_group_id
started_at / ended_at
returncode
stop_reason
failure_stage
message
```

### Immutable Launch Snapshot

启动顺序：

1. 重新执行 Preflight。
2. 解析训练模型资源或 legacy 路径。
3. 将 profile、RL、Sampling、GPU 和模型来源合成为有效配置。
4. 创建 run 目录并原子写入快照。
5. 让 `train_tir_agent.py --rl-yaml` 指向 `effective-rl.yaml`。
6. 使用快照旁的 Workflow 解析 Sampling，不再读取可编辑实验文件。
7. 启动成功后进入 `running`，启动失败写入 `failed`。

`launch.json` 记录 Git commit、脱敏 argv、模型来源 ID/修订、GPU、profile、算法和快照校验值。API Key 和完整环境变量禁止写入。

### Concurrency and Idempotency

新启动接口建议为：

```text
POST /api/rl/runs
```

请求携带：

```text
experiment_id
preflight_revision
stop_local_llm
request_id
```

- `request_id` 防止网络重试重复创建训练。
- Preflight revision 过期返回 409，要求重新确认。
- 已有训练占用同一 GPU 时返回 409，并返回活动实验和 run ID。
- 不再通过 `replace=True` 隐式停止训练。
- 允许将来扩展互不冲突 GPU 上的并发运行，但首期可以继续全局单训练，只要明确返回冲突。

### Safe Stop

新增：

```text
POST /api/rl/runs/<run_id>/stop?experiment_id=<id>
```

停止过程：

1. 校验 run 属于实验且状态可停止。
2. 原子标记 `stopping`，拒绝重复停止。
3. 对进程组发送 `SIGINT`。
4. 等待正常退出并保存 checkpoint/日志。
5. 超时后发送 `SIGTERM`，最后才使用 `SIGKILL`。
6. 标记 `cancelled` 和停止原因。

已完成运行再次停止应返回幂等结果，不把成功运行改成取消。

## API Contract

```text
POST /api/rl/runs
GET  /api/rl/runs?experiment_id=<id>
GET  /api/rl/runs/<run_id>
POST /api/rl/runs/<run_id>/stop
```

运行详情返回 `state`，迁移期同时保留派生的 `running` 字段。旧 `/api/runs` 可以映射到新读取层，避免一次性破坏 Monitor。

错误响应包含稳定 code：

```text
preflight_failed
preflight_stale
training_conflict
run_not_found
run_experiment_mismatch
run_not_stoppable
process_start_failed
```

## UI Behavior

本阶段只建立正确命令，不完成最终控制台：

- Preflight 通过后显示确认摘要。
- 点击确认只提交一次，等待服务端返回真实 run ID。
- 返回成功后显示 `starting/running`，不通过轮询“最新任务”猜测本次 ID。
- 冲突时展示正在运行的实验和“查看该训练”，不提供覆盖启动。
- 停止按钮绑定当前 run ID；切换实验不会误停其他任务。
- 启动请求断开且结果未知时先按 `request_id` 查询，不自动重试创建。

## Implementation Notes

- `ProcessManager` 使用 `preparing / starting / running / stopping /
  succeeded / failed / cancelled / interrupted` 状态机，状态文件采用临时文件替换，
  避免写入半截 JSON。
- Windows 子进程使用独立进程组；停止先发送中断信号，超时后依次升级
  `terminate` 和 `kill`。Linux 保持进程组 `SIGINT` 行为。
- 服务重启后，磁盘中没有受管进程身份的活动态记录标为 `interrupted`，不再仅通过
  可能被复用的 PID 宣称训练仍在运行。
- `launch_training()` 在单一命令锁内处理 request ID、Preflight revision、
  冲突检查、快照写入和进程创建。相同实验与 request ID 的重试返回原 run。
- 每次训练写入 `effective-rl.yaml`、`effective-workflow.yaml` 和
  `launch.json`；Control 启动时向 `train_tir_agent.py` 显式传入两个快照路径。
- 新接口为 `POST/GET /api/rl/runs`、`GET /api/rl/runs/{run_id}` 和
  `POST /api/rl/runs/{run_id}/stop`。旧 `/api/rl/train` 与 `/api/rl/stop`
  继续调用同一实现。
- React Provider 保存服务端返回的准确 run ID；状态轮询按该 ID 读取，停止也只提交
  该 ID。已知服务端错误会清除 request ID，网络结果未知时保留 ID用于幂等恢复。
- 自动验证使用短生命周期 Python 子进程覆盖成功、失败、冲突、取消、归属校验、
  磁盘恢复、快照和幂等重试，不启动训练模型或 GPU。

## Lightweight Validation

默认只做无需 GPU 的快速检查：

```bash
python -m compileall science_infra/control mas/train_tir_agent.py
cd webui && npm run build
```

用短生命周期假子进程验证状态迁移、冲突、定向停止和快照文件，不启动 VERL 或加载模型。真实训练启动与停止由用户在第四阶段通过 WebUI 手动验收。

## Acceptance and Delivery Boundary

- 两次重复提交同一 `request_id` 只产生一个 run。
- 实验 A 训练中，从实验 B 点击停止不会终止实验 A。
- 已有训练时再次启动返回明确冲突，不替换旧进程。
- 运行开始后编辑实验 YAML 不改变本次快照。
- 启动失败、非零退出和用户停止分别显示不同终态。
- 本阶段完成后运行控制可信，但日志仍可使用轮询降级；实时控制台属于第三阶段。

## Risks and Edge Cases

- PID 存活不等于原训练仍存活；恢复状态应同时核对进程启动信息或将无法确认的任务标记为 `unknown/interrupted`。
- 快照写入成功但进程创建失败时必须保留失败记录，不能返回成功。
- 停止期间服务重启可能留下子进程；状态恢复和进程身份校验要有明确降级。
- `SIGINT` 是训练保存退出的首选，但第三方组件可能不响应，超时升级策略必须可见。
